# 照片 PPLUT 实现笔记

地址取自 ILCE‑6700 2.00。AP 表中是 `appFw.so` 的 ELF 虚拟地址，定位实际进程地址时须按对应段计算装载偏移。CP 表中是以 `0x108000` 为基址解析 `cpapp-b.bin` 得到的地址，使用 ARM 或 Thumb 时遵循原函数的调用约定。下表中的名字多为研究时按行为的命名。旧的进程 ID、共享句柄、任务地址和全部日志游标均只对当时开机有效。 [输入文件指纹](复现与续接.md#研究输入)

## AP 从照片 PP1 借用视频绑定

| 调用点或消息 | 观察及实验用法 |
| --- | --- |
| `0x334e224 → 0x3216168` | LUT 资格检查。照片 context 2 被拒绝，视频 context 3 有效。照片 PP1 路径只把这次调用的局部 context／PP 改为 3／12。 |
| `0x334e330 → 0x3215fc0` | 解析 PPLUT 绑定，此次调用采用 PP12 对应 PPLUT1。context 5 的直接选择是另一条路径，照片实验沿原生绑定和槽位保持索引随菜单变化。 |
| `0x3440d50 → 0x3440aec`、`0x34d22f4 → 0x176a090` | 取得 LUT 文件与描述符，走原 AP 提交。回调查找在 `0x34d1ef8 → 0x34d1db0`，释放调用点为 `0x3288f74`。AP 回调到达仍需独立核对 CP 已完成哪一代 LUT、由哪条照片任务持有。 |
| AP `0x34f4608` 发送 `0x4155` | CP 接收端 `0x351200` 存储描述符和代际状态。可在原提交周围确定本次 descriptor／generation。 |
| AP 基础参数 `0x34e93b0／0x34e9400`、`0x4157` | 原照片路径给出 base look 11、shooting mode 3。CP 接收端有 `0x8bff82`。历史 B 组把本地输入改为 `[10,0,1,1,0]`，同一模式下实际 LUT acquire 索引仍以原助手结果为准。 |
| AP 输出 `0x34e934c`、`0x4154` | CP `0x351158` 把五个 AP 布尔合成四个策略位（Main／Mon／Ex∣HDMI／Ex∣SDI）。旧实验仅置其余四个参数，Main 保持原值。 |

保持照片挡原菜单 PP1、Log 设置、全局 general mode 和 PPLUT 文件绑定。调试时先用明显能区分两份 LUT 的诊断绑定。显示链与主图链分别采集。 [早期生命周期源码](tools/native/ap-lifecycle-0.5.0/) · [照片资格适配器](tools/native/photo_lut_context_adapter.c) · [AP 覆盖源码](tools/native/ap-override-0.3.0/) · [最后一轮 AP 加载器差异](tools/native/ap-capture-loader-0.3.1/)

## CP 从描述符到照片主图

1. **配置与选择。** CP `0xb10682` 构造任务参数，`0xb15d30` 在原照片 shooting mode 3 下采用 base look 11。LUT ID 选择见 `0x4dcab8`，传参见 `0x4dc7c8`（SetVfxMlutParam）。User3D 与 ArtGen 入口分别在 `0x542108`、`0x542344`。原生异步回调 `0x4dca4c` 在成功路径清除等待。视频实机可稳定见到 `state=2, wait=0`，这是一段全局状态，不能据此把完成归给随后一张照片。 [就绪回放](tools/emulate_cp_lut_readiness.py)
2. **照片资源。** 原 `StartVFX 0x475768 → 0x541974` 使用 `mode=0/kind=1`，归属相关入口在 `0x541734`。四条带均用 selector 4。测试中直接套视频 `mode=1/kind=2` 命中拒绝状态 5。应保留照片原资源类型，在实际持有的同代对象上进入原生准备 `0xb96862`。AP DMM 的映射、关闭、释放是不同阶段，`0x21 mode 1` 可保持映射和引用，`0x25` 关闭映射，`0x23 mode 2` 同时释放。本次资源的生命周期跨过回调，完成或释放时单看数字句柄可能混淆重用。 [DMM 回放](tools/emulate_pp1_dmm_provider.py) · [持有与回执协调原型](tools/native/photo_pp1_lut_coordinator.c)
3. **主图支路。** 照片任务在 `task+0x5b04` 保存“main image”相关缓冲，`0x480d82` 在原照片构建时将其 LUT 开关置零。CP `0xb97516` 受 `0xb95cfa` 激活位 21 和 Main 决策影响。回放中 Main=0 时绕过，Main=1 且激活时在 6192×4128、stride 6272 的同一主图内处理四条 1548×4128 条带。四个条带及归属条件按当次任务分别核对。 [照片主图回放](tools/emulate_cp_photo_jpeg_route.py)
4. **JPEG 交接。** `0x48220c → 0x481aa8 → 0x473688 → 0x5226ec／0x52279c` 传递主图描述符到编码器提交。原 CP 片段在回放里确实消费这个缓冲。硬件提交、时钟、调度和像素处理采用夹具，完成日志也可能来自 MPF 辅助图，最终要用主 JPEG 像素验收。VEF 备选分支的虚表和 91 组参数已离线定位，回放未建立其与照片主图的关系。 [JPEG 解码和回放](tools/emulate_cp_jpeg_native_records.py) · [VEF 回放](tools/emulate_cp_vef_mlut.py)

每次照片取证应绑定 AP 描述符、CP 当前 generation、照片任务和 owner、LUT 与 VFX handle、selector 和回执状态，确认最后一条带结束、回调排空、资源归还。观察到重复 LUT handle 或全局 `wait=0` 时仍需检查任务归属和晚到回调。 [历史记录器](tools/native/cp_pp1_capture.c)

## 原生环形日志与查询通道

- `ULOG` 头大小 60 字节。固件默认目录有 79 个 `SUBS`，可离线运行原构造、查找与区域选择。VFX `0x67` 的固定观测区归一到 area 0（2084 字节），MLUT `0x2ae` 用 area 1（4132 字节），JPEG 是另外一路。边界校验覆盖 `RBUF` 标记、两个游标、占用量、计数和记录跨度。指针、互斥字段和短期重读仅用于结构核对。同值的前后头仍可能发生回绕或 ABA。 [VFX／MLUT 解码](tools/cp_native_log_records.py) · [JPEG 解码](tools/cp_jpeg_log_records.py)
- `osal_ulogio.ko` 的 AP 日志代理 `0x808f084a`，处理函数偏移 `0x5570`，会转发到 `0x908f084b` 后重组返回结果。用 stock 指令回放，CP 原始返回 `0x80` 或候选返回 `0x5A`，AP 这层都给出 `0x80`。选用 `0x908f084b` 的直连消息、选择器 `0x43` 后才取得有效执行对照。字节回读、直连应答和 USB 枚举分别记录。 [代理对照](tools/emulate_ap_log_proxy_status.py) · [固定选择器候选源码](tools/native/cp_selector_status_canary.c)

## CP 早期引导与故障采集

照片记录器在原 `0x108728` 调用点把 `BL 0x108070` 改为 `BL 0x10f000`。这在 ARM 早期映射/清零链中执行，候选再走原入口。历史构建测试把完整候选镜像预置到 Unicorn 内存，验证了后续映射项。当冷启动加载集合、装载顺序或可执行性不同，仅用存储回读和完整镜像夹具覆盖不到这次先跳转再建立记录页的依赖。

| 离线条件 | 观察 |
| --- | --- |
| 原镜像／预置完整候选镜像 | 均能到原 `0x108070`。候选经过 `0x10f000` |
| 记录器目标页不存在 | 在 `0x10f000` 的取指失败 |
| 记录器目标页为零 | 顺序执行至夹具中的 `0x111000` 边界失败 |
| 原等待条件未满足 | 指令预算用尽，留在原等待点 `0x108980` |

原 CP 已有异常保存代码。后期入口在 `0x609858` 设置 VBAR 到 `0x128180`，`0x60dad4` 建立异常栈，`0x60da5c` 保存寄存器。真实早期故障能否到达这些路径，以及保存内容能否通过 AP、独立串口或其他恢复入口读出，仍无证据。AP 引导器中可见 DDR 日志分支，机身本轮未读到这些内容。下一轮故障记录设计应在原早期引导保持可达的条件下验证唯一心跳、超时和异常出口。记录机制本身需独立于被测回调与 MSC 菜单。 [历史引导改动](tools/native/cp_pp1_capture.S) · [离线复盘代码](tools/replay_cp_boot_fault.py)
